# Release hardening

## Decisions

- **End-to-end tests use Maestro, run on a simulator build.** Expo's docs recommend it, and it needs no library inside the app, so it changes nothing about how releases go out.
- **The app's dev build turns off PostHog error tracking only.** Analytics and session replay stay on in development. Dev-only errors, like a missing native module on an old dev build, were filling the error list.
- **An error without a stack trace is grouped by its message, through `before_send` in `features/general/posthog/client.ts`.** PostHog gave every such error the same fingerprint, so different problems landed in one row. PostHog grouping rules were dropped because they need one rule per kind of error.
- **A render error is caught by a per-screen boundary, with the root `ErrorBoundary` as the backup.** The per-screen one keeps the rest of the app working. Its setting is named "unstable", and nothing fails if an Expo update drops it, so the root one stays as a backup and also covers layouts and providers.
- **The error screen uses `InnerScreen` when there is a screen to go back to.** The broken screen's own header goes away with it, so without this the back arrow is lost. On a screen with nothing behind it, like Home, the error screen keeps only "Try again".
- **The error screen shows "Something went wrong. Try again." from `getErrorText`, not the error's message.** A render error's message is a programmer message, like "TypeError: undefined is not an object". PostHog still gets the full error.
- **The error boundaries don't send the error to PostHog themselves.** React Native already logs a caught render error with `console.error`, and PostHog's console capture reports it once, with its stack trace. Sending it again would count it twice.
- **Lint runs `no-floating-promises` and `no-misused-promises`, but skips handlers passed to props like `onPress`.** Most of those handlers already catch their own errors, and checking them would need a wrapper on about 30 of them. The lint takes about 3 seconds longer, because these rules read type information.
- **A call that can't fail gets `void` and a comment saying why, not a `.catch`.** The trailer player's calls, the volume reading and `useRefreshQuery`'s refresh all only ever resolve, so a `.catch` on them could never run.
- **A failed Save, rating or Unseen is logged with `console.error` and shown as "Couldn't save your change".** The backend sends its own errors, like "Item is already saved", which mean the app and backend disagree, so PostHog has to see them. The toast's second line comes from `getErrorText`. The toast is written inline in each handler, like every other toast in the app.
- **A failed logout keeps the sheet open, and the global `Toast` sits outside `BottomSheetModalProvider`.** The sheet library draws open sheets in a layer after everything inside its provider, so a toast inside it showed dimmed under the sheet's backdrop. Moving the toast out fixes this for every sheet.
- **A failed request throws an `APICallError`, and its `status` is set only when our backend answered with its error format.** Before, an answer in another format got a status with an empty message, and an empty answer got no status. Now a status always means the message is the backend's own text and safe to show. `fetcher` wraps only failed requests, so a bug in our own code isn't shown as a connection problem.
- **Every error text comes from `getErrorText`, which checks the error with `instanceof` instead of `error as Error`.** It shows the backend's message when there is one, "We couldn't reach Meowie. Check your connection and try again." when the request got no answer from our backend, and "Something went wrong. Try again." for anything else. A second argument changes that last text, so the Google and Apple sign-in toasts pass 'Try "Continue with Email" instead'. Errors from the sign-in libraries are checked without casts: Google's with the library's own `isErrorWithCode`, Apple's by checking for `code` in place, because Expo turns iOS native errors into `CodedError` only on Android as far as the code shows.
- **The Google and Apple sign-in failure toasts point the person to the email code login.** Both fail on some devices with errors the app can't fix, and the email code still works there.
- **"Privacy policy" has no failure toast, and "Empty cache" has no `try`/`catch`.** On iOS, `openBrowserAsync` only throws for a URL that isn't valid, and ours is fixed. `Image.clearDiskCache` only resolves, and `invalidateQueries` never rejects without `throwOnError`. So a toast or a catch there could never run.
- **When the feedback survey hasn't loaded, "Send" logs with `console.error`, shows "Couldn't send your feedback" with "Try again.", and reloads the survey.** Without the reload, the next tap would fail the same way until the app comes back to the foreground. The typed text stays in the field.
- **"Empty Cache" shows its loading state until the clear is done, then closes the sheet.** The clear waits for every cached query to reload, which took several seconds on the simulator, and before this the sheet gave no sign it was working.
- **The splash waits for the first try of `/user/current` only.** With all four tries, a backend that hangs could hold the splash for up to 49 seconds. After a failed first try the app opens as it did after all tries failed: an onboarded person goes to Home and keeps their session, and the query keeps retrying.
